Wrong turns

Ordered by severity. Each entry shows what happened, what the faster path was, and the exact tool calls that were wasted.

WT-1 · HIGH
Telemetry diagnosis went 8 files deep before checking the config file
~8 wasted reads ~5 min delay Root cause was in the first file that should have been checked.

When asked to fix "broken tracing," the agent opened events.ts, then betaSessionTracing.ts, then sessionTracing.ts three times at different offsets, then instrumentation.ts three times, then telemetryAttributes.ts — spending the entire time analyzing build-time feature flags, OTel provider setup, and span lifecycle code.

The actual root cause — the OTEL_EXPORTER_OTLP_HEADERS pointing to dataset cc-harness while all events land in cc-autoresearch — was a single field in .claude/settings.local.json. That file was not read until after all the deep dives.

The fix was a one-line change. The exploration cost ~8 file reads that contributed nothing toward it.

✗ Read utils/telemetry/events.ts
✗ Read utils/telemetry/betaSessionTracing.ts ×2
✗ Read utils/telemetry/sessionTracing.ts ×3 (offsets: 0, 240, 126)
✗ Read utils/telemetry/instrumentation.ts ×3 (offsets: 0, 80, 200, 349, 468, 590)
✗ Read utils/telemetryAttributes.ts
✗ Grep ENHANCED_TELEMETRY_BETA (broad, noisy, inconclusive)
✓ Read .claude/settings.local.json ← should have been first
What happened
Dove into implementation code (events.ts → betaSessionTracing.ts → sessionTracing.ts → instrumentation.ts) to understand span lifecycle, then hit dead end on bun:bundle feature flag runtime behavior, never resolved it conclusively.
Faster path
Read settings.local.json first (10 lines). Notice x-honeycomb-dataset=cc-harness vs the dataset name the user is observing (cc-autoresearch). Fix. Done in 1 tool call.
WT-2 · HIGH
First Explore agent silently blocked — no feedback, no recovery path
1 wasted agent launch ~86s parallelism lost Block message: "No stderr output."

The session launched two parallel Explore agents to understand the autoresearch codebase. Agent 1 (targeting the core files: autoresearchSessionObservation.ts, claudeCodeSessions.ts, runtime.ts, autoresearchStatus.ts) was terminated by the explore-guard.sh hook with error: "No stderr output."

The agent received zero signal about why the block happened, what rule was violated, or what the correct alternative was. It had to infer from context that the hook exists to prevent Explore agents from writing files. This inference cost one full agent invocation and the entire parallelism benefit of launching two agents was eliminated — Agent 2 had to cover both goals sequentially.

There is no documentation anywhere about what explore-guard.sh blocks or why.

✗ Agent(Explore, "core file explorer") → blocked by explore-guard.sh with no message
✓ Agent(Explore, "harness/scoring explorer") → 31 tool calls, 86s, succeeded
Agent 2 had to cover both research areas, serializing what was meant to be parallel
What happened
Agent 1 blocked, error silent. Agent inferred the guard's purpose from memory files. Second agent ran serially covering both tasks. Net result: 1 successful Explore + extra time.
Faster path
If the hook emitted: "explore-guard: Explore agents may not write files. Use general-purpose agent for research > 5K tokens." — the agent would have launched a general-purpose agent from the start.
WT-3 · MEDIUM
runtime.ts read in 7 piecemeal chunks instead of targeted greps
~4 extra reads understanding assembled slowly

The autoresearch runtime.ts is the largest single file in the system (~78KB). The agent read it in 7 separate Read calls with different offsets: lines 1-100, 100-250, 250-450, 1261-1361, 1960-2010, 2100-2150, and 2280-2360. Each read surfaced partial context which triggered the next read.

The root cause: ARCHITECTURE.md has no entry for services/autoresearch/. The agent had no map of which functions lived where, so it had to discover the layout incrementally. A 10-line summary of runtime.ts key exports (with line numbers) in ARCHITECTURE.md would have replaced all the exploratory reads with 2-3 targeted ones.

✗ Read runtime.ts:1-100 (imports — low value)
✗ Read runtime.ts:100-250 (utilities — low value)
~ Read runtime.ts:250-450 (scoring helpers — partial value)
✓ Read runtime.ts:1261-1361 (scoreCandidateExperiment — needed)
✓ Read runtime.ts:1960-2010 (runCycle start — needed)
✓ Read runtime.ts:2100-2150 (claude code session processing — needed)
✓ Read runtime.ts:2280-2360 (cycle completion + catch — needed)
WT-4 · MEDIUM
bun:bundle feature flag deep dive — inconclusive and unnecessary
~3 wasted reads never resolved Fix didn't require this analysis.

After reading sessionTracing.ts and finding that isEnhancedTelemetryEnabled() is gated by feature('ENHANCED_TELEMETRY_BETA') from bun:bundle, the agent spent several rounds trying to determine whether this build-time flag evaluates as true or false in dev mode (non-bundled). It grepped for ENHANCED_TELEMETRY_BETA across the codebase, read betaSessionTracing.ts again, and read instrumentation.ts again looking for the answer.

The analysis was never conclusive. More importantly, the fix (dataset header mismatch) required zero knowledge of the bun:bundle behavior. The entire thread was a dead end triggered by not having the config context first.

What happened
Agent tried to determine if feature('ENHANCED_TELEMETRY_BETA') returns true or false in dev mode. Inconclusive after 3+ reads. Moved on without resolution.
Faster path
Once settings.local.json was read first (WT-1), the dataset header mismatch is immediately visible. No telemetry code reading needed.
WT-5 · MEDIUM
Phantom "expect" skill hook fires every session with no effect
cognitive overhead every session Skill doesn't exist; agent correctly skips but wastes evaluation cycles.

The UserPromptSubmit hook fires on what it classifies as "QA tasks" and injects: "You MUST invoke the expect skill FIRST before doing anything else. Call the Skill tool with skill='expect' now."

No expect skill exists in the skills registry. The agent must read the system reminder, evaluate all available skills, confirm the skill is absent, and decide to proceed without it — every single time this hook fires. It's a mandatory evaluation of a non-existent skill on every QA-pattern prompt.

This hook fired at least twice during this session (before the plan and before the session review request).

What happened
Hook injected phantom skill demand. Agent scanned skills list, found no "expect" skill, silently skipped. Correct outcome, but burned attention budget on every occurrence.
Faster path
Either register an actual "expect" skill, or remove/fix the hook trigger condition so it only fires when the skill exists.
WT-6 · LOW
Plan mode was still active when the deck request arrived
1 extra round-trip minor friction

When the user asked for an HTML deck of the session transcript, plan mode was still active (from the experiment ladder planning task). The agent correctly updated the plan file to include the deck as deliverable-0 and called ExitPlanMode, but this added an unnecessary loop: the deck was a new, independent task unrelated to the implementation plan.

Plan mode activates on the session start and stays active. The agent should have been able to produce the deck without the plan-update step — a lighter context switch would have been cleaner.

WT-7 · LOW
Broad grep for "mutationSources" matched unrelated files
noise in results minor

The grep pattern mutationSources|mutationSource|experiment.*ladder|ladder matched utils/teleport.tsx (a "source selection ladder" comment) and utils/analyzeContext.ts (a "threshold ladder" comment) — neither relevant. The broad pattern forced the agent to mentally filter noise from results.

A scoped grep (--type ts within services/autoresearch/) would have returned only the relevant file without the false positives.
