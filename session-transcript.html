Why invoked: The using-superpowers skill mandates checking for relevant skills before any action. The agent scanned the available skill list and selected objective-research because the task involves researching a codebase — the word "research" created a surface-level match.
⚠ Decision Point — Skill Mismatch

The objective-research skill is designed for pre-implementation context separation: you hide a feature ticket from a research agent to prevent confirmation bias. Its core insight — "research agent should not know what you're building" — is irrelevant here.

The task is "describe what exists", not "research before building". The correct skill match would have been brainstorming-planner (to scope what "analysis" means and what slides to produce) or no skill at all.

Cost: The skill loaded 2,800 words of guidance that were partially applied but mostly irrelevant. It influenced the decision to use a separate research agent (good) but added framing overhead (neutral/bad).

Post-Mortem — Points of Failure & Inefficiency

Root Cause Analysis

Ranked by impact on session efficiency. Each finding includes what happened, why, and what the correct behavior would be.

High Impact F1 — Wrong skill invoked at the start
What happened: The agent invoked objective-research for a "describe what exists" task. This skill is designed for pre-implementation research where you hide a feature ticket from a research agent to prevent confirmation bias.

Why it happened: The skill selection heuristic is surface-level keyword matching. "Research the codebase" → objective-research. The agent didn't evaluate whether the skill's core mechanism (context separation to prevent intent leakage) was relevant to a descriptive analysis task.

Impact: ~2,800 words of skill guidance loaded into context that were partially irrelevant. The skill's framing ("hide the ticket") caused the agent to construct an elaborate 15-question prompt rather than asking the Explore agent to "give me a comprehensive technical overview."

Correct behavior:
  • For "analyse and present" tasks → invoke brainstorming-planner first to agree on scope and slide structure, then explore
  • Or invoke no skill — a direct Explore agent call with a well-scoped prompt would have been faster
High Impact F2 — 83k token research result loaded into main context (not offloaded to file)
What happened: The Explore agent returned ~83,000 tokens of research findings. These were loaded directly into the main conversation context and processed in-place.

Why it happened: The Agent tool returns results inline — there's no automatic file offload. The agent didn't add an intermediate step to save the findings.

Impact:
  • Main context grew by ~83k tokens in one turn
  • Follow-up tasks (like this transcript generation) start with a heavily loaded context
  • The HTML slide generation had to "see" all 83k tokens even though each slide only needed ~500 words of findings
Correct behavior: After the Explore agent returns, write findings to research-findings.md, then load sections selectively while writing each batch of slides. The context-window-management skill explicitly covers this.
Medium Impact F3 — 15 questions covering every subsystem equally, no prioritization
What happened: The agent asked 15 broad questions covering every major directory. The Explore agent spent equal time on high-value subsystems (AgentTool, QueryEngine) and low-value ones (Cost tracking, Remote server) for a slide deck.

Why it happened: The agent had no scoping input from the user ("deep analysis" is maximally broad), and the objective-research skill encouraged exhaustive questioning. The agent defaulted to "describe everything."

Impact: The 45-tool-call, 283-second exploration likely could have been 20–25 tool calls in ~150 seconds with 8–10 targeted questions focused on the most architecturally interesting parts.

Correct behavior:
  • Ask the user: "Do you want coverage of every subsystem or focus on the novel/interesting architectural decisions?"
  • Or use brainstorming-planner to define the slide structure first, then research only what each slide needs
Medium Impact F4 — No upfront scope agreement with user before starting research
What happened: The agent went straight from "first do a deep technical analysis" to exploring the codebase without asking what "deep" means, what audience the deck is for, or how many slides were expected.

Why it happened: The CLAUDE.md instructions say "State the goal, check existing code, ask if unclear" but the agent interpreted the task as clear enough to proceed. "HTML slide deck" + "deep technical analysis" felt complete.

Impact: The agent produced 19 slides. The user might have wanted 10 high-density slides, or 30 granular ones, or wanted it focused on the multi-agent architecture specifically. We got lucky that the output matched expectations.

Correct behavior: One quick clarifying question: "Should I cover all subsystems (~19 slides) or focus on specific areas? Is this for a technical audience familiar with the stack or an introduction?"
Low Impact F5 — Unnecessary ls of parent directory (my projects/)
What happened: Step 5 listed the my projects/ directory (30+ unrelated projects). This data was never used in the analysis or slide deck.

Why it happened: Habit-driven exploration. When the agent runs ls on a directory, it also checks the parent to understand context. This is useful in some situations (e.g., understanding monorepo structure) but not here.

Impact: Minimal — parallel call so no added latency. The result just added noise to context.

Correct behavior: Only explore what's needed for the task. The contents of sibling projects are irrelevant to analyzing one specific project.
Low Impact F6 — design-html skill not invoked before writing the deck
What happened: The design-html skill ("generates production-quality Pretext-native HTML/CSS") was available but not invoked before writing the slide deck.

Why it happened: The skill description says it "works with approved mockups from /design-shotgun" — implying a multi-step design workflow the agent correctly judged as overkill for this task. The agent proceeded with its own HTML implementation.

Impact: Negligible — the output deck was high quality. The skill might have added CSS conventions or design system tokens, but the custom implementation was solid.

Verdict: This was actually the right call. Not every skill should be invoked.

Key Takeaways
What hurt performance
  • Skill invocation adds latency and context load even when the skill is wrong — the check is mandatory but the selection logic is shallow
  • No scoping conversation with user → defaulted to maximum coverage
  • 83k tokens of research findings inline in main context = expensive follow-up turns
  • 15 questions = 283s. 8 questions = ~130s. Scope is the biggest lever
What worked well
  • Reading package.json first was high signal / low cost — correctly identified the project type
  • Using a separate Explore agent kept research noise out of main context
  • Parallel Bash calls (steps 4–7) were correctly batched
  • Single-shot HTML write with 19 accurate slides — no iteration needed
  • The research agent's output was genuinely accurate with correct file:line citations
