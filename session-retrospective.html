Wrong Turns — Detailed Analysis

7 identified
1

WT-1 — Wrong skill invoked: brainstorming-planner

High Impact

What happened: The first action after receiving the task was to invoke the brainstorming-planner skill. This skill is documented as "Use when starting a complex project, task, or feature to deeply clarify requirements, identify scope boundaries, map dependencies" — a pre-build planning tool.

Why it happened: The using-superpowers meta-skill mandates checking for skills before any response. The agent scanned the list and matched on: "complex task" + "codebase" + "presentation." brainstorming-planner was the closest match by keyword proximity, not by core mechanism fit.

What was invoked
brainstorming-planner
Designed for: planning a feature build
Output: 3k words about acceptance criteria, phasing, risk identification — all irrelevant to "describe what exists"
What should have been invoked
No skill — or a 1-line scope check:
"Should I cover all subsystems (~20 slides) for a technical audience, or focus on specific areas?"
Then go straight to exploration.
⚠

Cost: ~3,000 words of irrelevant guidance loaded into context. The skill guided the agent to ask "what does done look like?" and "define acceptance criteria" — framing that added overhead to what should have been a direct exploration task.

Corrected at: The agent recognized the skill content was mismatched and pivoted after Step 2 to direct exploration without following the skill's suggested workflow. Self-correction was fast but the context cost remained.

2

WT-2 — Write failed: "File has not been read yet"

High Impact

What happened: After gathering all research, the agent attempted to Write to analysis-deck.html. The Write tool requires a prior read of any existing file. The tool returned an error.

Recovery path (3 extra steps):

Write → ERROR: "File has not been read yet. Read it first."
Bash: ls analysis-deck.html && echo "exists" → "exists"
Read: first 5 lines of file (to satisfy the requirement)
Write: success ✓
What happened (4 calls)
Write → fail
Bash exists check
Read (5 lines)
Write (success)
What should have happened (1 call)
Check if file exists before writing.
If yes: Read first, then Write.
If no: Write directly.
→ Total: 1–2 calls max
✗

Root cause: The analysis-deck.html file already existed from a prior session. The agent didn't check for pre-existing files before issuing the Write. The tool contract was known (Write requires prior Read) but the pre-existence of the file wasn't checked first.

Corrected at: Immediately after the error. The agent correctly diagnosed the issue, did the minimal read (5 lines), then succeeded. But this wasted 3 tool calls and added latency.

3

WT-3 — Used Bash find and ls instead of Glob

Medium Impact

What happened: Initial directory exploration used Bash ls and Bash find -maxdepth 3 -type f. The find call returned 57KB of output — so large it was persisted to a temp file and only the first 2KB was available in-context.

Instruction violated:

// From system prompt:
"To search for files use Glob instead of find or ls."
"Avoid using this tool to run find, grep, cat, head, tail, sed, awk..."
What was used (Bash)
find "..." -maxdepth 3 -type f | head -60
Result: 57KB → truncated to 2KB
Output lost; required extra step to recover
What should have been used (Glob)
Glob("**/*.ts", path="src 2")
Returns sorted file paths directly
No truncation, respects tool boundaries

Why it happened: The Bash tool is more familiar and flexible. When exploring unfamiliar codebases the agent defaults to shell commands before checking if a dedicated tool covers the need.

Corrected at: Subsequent exploration steps correctly used the Read and Grep tools. The initial Bash habits weren't repeated.

4

WT-4 — Unnecessary ls of parent directory

Medium Impact

What happened: In the first parallel batch, the agent listed both the project directory and its parent (my projects/). The parent listing revealed 30+ unrelated projects (paperclip, spark, hermes, etc.) that were never referenced in the analysis or slide deck.

What was explored
ls /my projects/cc/ ← needed
ls /my projects/ ← never used
Output: 30+ unrelated project names
Correct scope
ls /my projects/cc/ only

Parent context irrelevant unless asked
"what workspace is this in"
ℹ

Why it happens: When a directory path contains a parent (e.g., my projects/cc), there's a habit of also checking my projects/ to understand whether this is a monorepo, workspace, or standalone. Here, it was clearly standalone and the extra check added only context noise.

Corrected at: Never — the habit fired and was never revisited. The data was simply ignored.

5

WT-5 — Used cat package.json via Bash instead of Read tool

Medium Impact

What happened: package.json was read with cat package.json | head -60 via Bash. The Read tool exists exactly for this purpose and is the mandated approach.

Instruction violated:

// From system prompt:
"To read files use Read instead of cat, head, tail, or sed."
⚠

Why it matters: The Read tool provides line numbers, respects malware scanning, and makes the operation visible to the user as a "file read" rather than a "shell command." Using Bash for file reads obscures intent and bypasses the tool's metadata.

Corrected at: All subsequent file reads used the Read tool correctly. This was a one-off early slip.

6

WT-6 — No upfront scope agreement before researching

Low Impact

What happened: The agent went directly from "deep technical analysis → HTML slide deck" to exploration without asking how many slides, what audience, what level of depth, or whether to focus on specific subsystems.

CLAUDE.md mandate violated:

"For deck / report / presentation tasks, also confirm scope before researching:
'I'll cover all major subsystems (~N slides/sections) for a technical audience.
Want me to adjust scope or focus on specific areas?'"
// One question, wait for answer, then proceed.
What happened
Went straight to exploration.
Produced 20 slides covering everything.
Got lucky — user didn't complain.
Correct approach
"I'll cover all major subsystems (~20 slides) for a technical audience — want me to adjust scope or focus on specific areas like the agent system or MCP?"
Wait 10 seconds. Proceed.

Corrected at: Not corrected — the agent got lucky that the output matched expectations. This is a latent risk: if the user had wanted 8 focused slides, the 283-second exploration would have been wasted.

7

WT-7 — Research findings not offloaded to a file

Low Impact (this session) · High Impact (future sessions)

What happened: The deep research (all the parallel reads across 20 files) was accumulated in-context and used directly for HTML generation. No intermediate research file was written.

CLAUDE.md mandate:

"When ANY tool or agent call returns > 5,000 tokens of output:
1. Write the full output to a temporary .md file
2. Show only a summary in the conversation
3. Reference the file path for all subsequent work"
⚠

Why it matters long-term: All the file reads — package.json, main.tsx, Tool.ts, tools.ts, Task.ts, QueryEngine.ts, plus all the ls outputs — are now in this context. The follow-up request (this retrospective) started with an already-heavy context, making it slower and more expensive than it needed to be.

Correct approach: After the exploration phase, write findings to research-findings.md, then reference sections of it during HTML generation. This keeps main context lean for follow-up tasks.

Custom slash command: /analyze

.claude/commands/analyze.md

Prevents: WT-1 (wrong skill), WT-6 (no scope), WT-7 (no file offload)

A custom slash command encodes the correct workflow for "analyze and present" tasks. When the user types /analyze, the agent follows this procedure instead of having to figure it out from scratch.

---
name: analyze
description: Deep technical analysis → HTML slide deck. Use for codebase analysis, architecture review, and technical presentations.
---

## Procedure

1. Read ARCHITECTURE.md and CLAUDE.md for instant project orientation.

2. Ask ONE scope question before any exploration:
   "I'll cover [N] major subsystems for a [technical/general] audience.
   Want me to adjust scope or focus on specific areas?"
   Wait for answer. Default: all subsystems, technical audience.

3. Explore using Glob and Read tools only (never find/ls via Bash).

4. Save all research to `research-findings.md` before writing HTML.

5. Before writing the output HTML file:
   - Check if it exists
   - If yes: Read it first (even 1 line is enough)
   - Then Write the full deck

6. Open the file in browser after writing.

This command would have short-circuited WT-1, WT-6, and WT-7 in one shot. The agent would follow the command's procedure instead of improvising from skill guidance.

What Went Well (for balance)

Good parallel batching

Steps 3–7 were correctly parallelized (multiple Bash and Read calls in a single message). The exploration was fast because independent calls ran concurrently rather than sequentially.

Single-shot HTML write

The entire 20-slide deck (1600+ lines) was written in one Write call. No iteration, no partial writes. This is optimal — all research was in context and used in one pass.

Accurate content

All 20 slides contained accurate file paths, type definitions, and function names. The direct file reading (rather than relying on memory) produced verifiably correct content.

Fast self-correction on WT-2

The Write error was immediately diagnosed and fixed in 3 clean steps. No thrashing or repeated errors. The error message was clear and the recovery path obvious.
